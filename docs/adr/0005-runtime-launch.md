# ADR 0005 — Только память запущенного процесса

Статус: принято. Дата: 2026-11-07.

## Контекст и решение

Пользователь предпочёл бы обойтись без изменения EXE. Ресурсов для 12
взаимодействий недостаточно, поэтому используются проверенные x86 callbacks
и декларативные изменения памяти. Исполняемый файл на диске остаётся исходным.

Сборщик читает локальный EXE, проверяет SHA-256, PE layout и исходные инструкции.
Игрок получает PAK, JSON-профиль, наш `callbacks.bin` и launcher. Патченного
игрового EXE, DLL-инжектора, службы и сетевого загрузчика в пакете нет.

Порядок запуска:

1. Проверить установленные файлы и точный EXE; убедиться, что эта копия закрыта.
2. Запустить собственный новый процесс из его `bin`.
3. Сохранить рабочую последовательность: 8 секунд ожидания, затем наличие окна
   с ограниченным ожиданием до 25 секунд; только после этого компилировать interop.
4. Проверить все live instruction sites до первой записи.
5. Выделить память callback, пересчитать внешние rel32 по таблице relocations.
6. Применить изменения, восстановить защиты страниц, очистить instruction cache.
7. Выдать `Spellbook12 is ready`. До этого не начинать и не загружать карту:
   book UI может создаваться ещё до первого явного открытия книги.

`0x11da000` — опорная VA при генерации байтов. Это не требование выделить память
именно там. Внутренние переходы и call/pop-таблицы сохраняются; внешние цели
явно релокируются. Для 5.5 адреса, globals и отличия регистров рассмотрены отдельно.

Ошибка останавливает только новый процесс, который запустил этот launcher.
Режима attach к уже идущему пользовательскому бою в выпуске нет.

Ресурсный PAK и runtime должны подключаться вместе. Для обычного запуска
через EXE/лобби без нашего launcher сначала нужен uninstall. Наличие PAK
с 12 привязками при исходных шестипозиционных инструкциях не является
поддерживаемым шестиячеечным режимом.

## Полученные шишки

Первый перенос launcher компилировал interop до запуска игры. Один свежий запуск
дал белое окно и падение; контроль со старым порядком и последующие свежие
запуски прошли. Сохранена рабочая последовательность. Это корреляция и
практический контроль, а не доказательство, что сама компиляция Add-Type вызывает
сбой движка. Фиксированное ожидание не считается универсальным сигналом готовности.

`WaitForInputIdle` подтверждает цикл сообщений, не загрузку 3D-движка. Новая
реализация readiness потребует отдельной проверки стартов и игрового меню.

Общий хук outliner может исполняться до открытия книги; «книгу не открывали»
не означает «наш код не исполнялся». Его fallback для чужих callers обязателен.

Ни перенос функций постоянным смещением, ни совпадение имени EXE не заменяют
проверку ABI, operands и исходных байтов. Не отключать проверки ради новой сборки.
